# 优化原理详解

> 🌐 **中文** | [English](Optimizations.en.md)

本文介绍为本项目新增/修改的核心优化（共 7 项）。所有优化都只在 `GGML_TYPE_Q1_0` 路径上生效，
不改变任何其它量化类型或后端的行为。

> ⚠️ 本文性能数据来自**单通道内存**测试机（8 GB DDR4-2666，流式读带宽约 14–17 GB/s）。
> tg 受内存带宽上限约束，绝对值偏低；双通道/更高带宽平台上的 tg 提升更接近内核层面。

---

## 优化 1：激活 per-128 量化（Q8_128）

### 问题

通用路径给 Q1_0 用的激活格式是 **Q8_0**（每 32 个值一个 fp16 尺度）。而一个 Q1_0 块是 128 权重
= 4 个 Q8_0 子块，4 个子块的尺度 `d1_0..d1_3` 各不相同。于是每个子块都必须单独做浮点转换：

```
Q8_0:  每 128 权重
  4 × ( vpsignb + dot + cvtdq2ps + fmadd + scale )    ← 4 次浮点转换
```

### 方案

把 tile 路径使用的激活量化改成 **每 128 个值一个尺度**（记作 Q8_128）：

```c
#define QK8_128 128
typedef struct {
    ggml_half d;        // 2 字节
    int8_t    qs[128];  // 128 字节
} block_q8_128;         // 共 130 字节 / 128 值
```

这样 4 个子块共享同一个 `d1`，可以把它们的 **int32 点积先累加**，最后只做一次浮点转换：

```
Q8_128: 每 128 权重
  4 × ( vpsignb + dot )  +  1 × ( cvtdq2ps + fmadd + scale )
                          ↑ 浮点转换 4 → 1
```

### 为什么实现成“局部格式”而不是新 GGML 类型

新增 `GGML_TYPE_Q8_128` 需要改动 `ggml.h`、`ggml.c` 以及 **175+ 个后端文件**的类型注册表，
风险极大且会波及 CUDA/Metal/Vulkan 等所有后端。

因此本实现只在 **q1t 路径内部**使用 Q8_128：

- 在 `ggml_compute_forward_mul_mat_q1t()` 里把 `src1->data`（F32）并行量化为 Q8_128，
  写入共享 scratch（位于 `params->wdata` 中 Q8_0 转换区之后），随后 `ggml_barrier` 同步。
- 通用路径（tg、尾部列、尾部行）仍使用框架已经量化好的 Q8_0，数值一致。

**开销可忽略**：量化处理 `ne11 × ne00` 个元素，而矩阵乘有 `ne01 × ne11 × ne00` 个 MAC，
比值为 `1 / ne01`（数千分之一）。

**精度**：per-128 比 per-32 略粗，但实测困惑度不升反降（见 [Correctness](Correctness.md)）。
这与 K-quant 使用 per-256 尺度的实践一致。

## 优化 2：寄存器分块 GEMM（2 行 × 4 列）

### 问题

默认 `ggml_compute_forward_mul_mat` 会为每个 (输出行, 输入列) 调用一次 `vec_dot`，
每次都**重新展开 1-bit 符号位**。对于 N 列的 prompt，同样的位展开被做了 N 次。

### 方案

把 R 行和 T 列放在寄存器里同时计算，符号位**每 R 行每 32 权重只展开一次**，供 T 列复用，
且**不落地到内存**（这正是早期“内存面板 panel”方案失败的原因——它额外写了 1 字节/权重再读回）。

核心循环（`q1t_dot<R,T>`）：

```c
for (ib : 每个 128 权重块) {
    for (k : 4 个子块) {
        sg[R] = expand(x[r][ib].qs[k]);        // 展开一次
        for (t : T 列) {
            qy = load(y[t][ib].qs + k*32);
            for (r : R 行)
                t32[r][t] += vpdpbusd(ones, sign(qy, sg[r]));   // int32 累加
        }
    }
    for (t,r)
        acc[r][t] = fmadd(d0[r]*d1[t], cvtdq2ps(t32[r][t]), acc[r][t]);  // 每 128 权重一次
}
```

### 分块尺寸的选择

`t32[R][T]`（int32）与 `acc[R][T]`（float）各占 `R×T` 个向量寄存器，加上 `sg[R]`、`d0v[R]` 等，
寄存器压力随 `R×T` 增长。实测（本机 AVX2，pp128）：

| R×T | pp128 (t/s) |
|----:|------------:|
| 4×1 | 12.30 |
| 4×2 | 14.55 |
| 4×3 | 15.27 |
| 3×3 | 15.67 |
| 4×4 | 15.85 |
| **2×4** | **16.36** |

因此最终选择 **R=2、T=4**：T=4 保证符号展开的摊销，R=2 控制寄存器压力。

## 优化 3：VNNI（`vpdpbusd`）

### 原理

AVX2 上计算 4 个 int8 乘积之和需要两条指令：

```
vpmaddubsw  ones, sy   → int16 成对和
vpmaddwd    ., ones16  → int32
```

VNNI 的 `vpdpbusd(acc, a_unsigned, b_signed)` 直接完成 `acc += a·b`（按 4 字节分组累加 int32）。
令 `a = ones`（无符号 1）、`b = sy`（有符号 ±q），则一条指令即可：

```
vpdpbusd  acc, ones, sy   → acc += Σ 4 个 sy
```

### 覆盖范围

| 指令集 | 宏 | intrinsic | CPU |
|--------|----|-----------|-----|
| AVX512-VNNI + VL | `__AVX512VNNI__` | `_mm256_dpbusd_epi32` | Cascade Lake / Ice Lake / Cooper Lake / Zen 4 / Sapphire Rapids |
| AVX-VNNI | `__AVXVNNI__` | `_mm256_dpbusd_avx_epi32` | Alder Lake |
| 无 | — | 回退到 `vpmaddubsw + vpmaddwd` | Haswell / Skylake-X / Cannon Lake 等 |

已通过反汇编确认（见 [Benchmarks](Benchmarks.md#vnni-指令确认)）：
`cascadelake` 797 条 `vpdpbusd`、`alderlake` 473 条、`haswell` 0 条（使用 993 条 `vpmaddubsw`）。

## 优化 4：`vpsignb`（“+1 保留 / −1 取反”）

1-bit 权重的核心语义就是：**符号位为 1 → 激活不变；为 0 → 激活取反**。这正是 `vpsignb` 的行为。

### 改进前

```c
sm = cmpeq(and(shuffle(...), bit_masks), zero);   // 0xFF 表 bit=0
sy = sub(xor(qy, sm), sm);                         // 两条指令，依赖链 2
```

### 改进后

```c
sg = or(sm, ones);                     // 0xFF (-1) 或 0x01 (+1)
sy = _mm256_sign_epi8(qy, sg);         // 一条指令
```

依赖链从 2 缩短到 1。独立微基准（单线程、热数据）：

| 内核 | GMAC/s |
|------|-------:|
| 原 `xor+sub` | 16.76 |
| **`vpsignb`** | **18.53** (+10.6%) |

该优化同时应用在：
- 通用内核 `ggml_vec_dot_q1_0_q8_0`（`arch/x86/quants.c`，AVX2 分支）
- 分块内核 `q1t_dot`（`q1t.cpp`）

## 优化 5：多微架构构建

通过 `-DGGML_BACKEND_DL=ON -DGGML_CPU_ALL_VARIANTS=ON` 把 CPU 后端编译成**每个微架构一个 DLL**，
运行时由 `ggml` 的加载器根据 CPU 特性选择最合适的一个：

```
x64  sse42  sandybridge  ivybridge  piledriver  haswell  skylakex
cannonlake  cascadelake  icelake  cooperlake  alderlake  zen4  sapphirerapids
```

- AVX2 及以上：启用寄存器分块 GEMM。
- 带 VNNI：额外启用 `vpdpbusd`。
- 更老的 CPU：回退到通用 Q1_0 内核（正确但较慢）。

见 [Compatibility](Compatibility.md)。

## 指令数对比（每 128 权重，AVX2）

| 阶段 | 通用 Q8_0 | 分块 Q8_128 | 说明 |
|------|----------:|------------:|------|
| 符号展开 | 4 × 5 = 20 / T | 4 × 5 = 20（摊销到 4 列） | 每 4 列一次 |
| 应用符号 | 4 | 2 | R=2 |
| 点积 | 4×(1~2) | 2×(1~2) | VNNI 各减 1 |
| 浮点转换 | 4 | 1 | **per-128 的关键收益** |
| 尺度计算 | 4 | 1 | |

综合实测 pp 提升 **29%–43%**。

## 优化 6：单列 GEMV（token 生成）

### 问题

tg 每次只解码 1 个 token（`src1->ne[1] == 1`），不会进入上面的分块路径，而是走通用
`ggml_vec_dot_q1_0_q8_0`。该内核使用 Q8_0 激活（每 32 权重一个尺度），因此一个 128 权重的
Q1_0 块必须做 **4 次浮点转换**（每个子块一次），且每次都带一条 fmadd 依赖链。

### 方案

对 tg 复用同一套 per-128 激活（Q8_128）：4 个子块的 int32 点积先累加，整个块只做
**1 次浮点转换**。行分组大小 `R` 默认 1（`q1t_gemv<1>`），可用 `GGML_Q1_GEMV_ROWS=2|4`
把激活加载在 R 行间共享。

同时把激活量化改为 **AVX2 向量化 + 按 128 值块跨线程分配**：单列时只有一行激活，若按行分给
线程则只有一个线程工作、其余在 barrier 空等；按块分配后所有线程都能并行。

### 效果

| 平台 | 内核（微基准，单线程） | 整模型 tg（12 线程，同场 A/B） |
|------|----------------------:|------------------------------:|
| i5-10400（AVX2，无 VNNI） | ~18.5 → ~24 GMAC/s（+30%） | ~11.2 → ~12.8 t/s（+13%） |

单通道内存带宽是本机 tg 的硬上限（`1.06 GiB / 带宽`）；内存带宽越高的平台，收益越接近内核层面的 ~30%。

## 优化 7：二值查表（Q1LUT，默认启用）

> 默认启用；`GGML_Q1_LUT=0` 关闭整个查表路径，`GGML_Q1_LUT_PP=0` 只关闭批处理（pp）查表。
> 代码全部在 `q1t.cpp` 内，不引用任何第三方实现。

### 思路（对照 BitNet TL，但适配二值）

BitNet 的权重是三值 `{-1,0,+1}`，无法用单条 `vpsignb` 表达，因此 TL 内核把权重预计算成
“按激活查表”。Bonsai 的 Q1_0 权重只有二值 `{-1,+1}`，符号位直接对应“保留/取反”，所以**不能**照搬
BitNet 的“每权重一张 16 字节表”——那会变成 16 字节/权重（约 128 倍膨胀），在带宽受限的 CPU 上必输。

二值下正确的查表方向是**激活侧**：一组 4 个连续权重只有 `2^4 = 16` 种符号组合，对一条激活向量，
为每 4 个激活预计算一张 16 项表

```
T[c] = Σ_{i=0..3} ( bit_i(c) ? +a[i] : -a[i] )
```

于是这 4 个权重的部分点积 = 一次 `vpshufb`（以打包的 4 bit 权重码为索引）。表按激活向量构建一次，
在该层所有输出行之间复用——这才是“二值查表”真正能摊薄成本的地方。

### 实现要点

- 表项是 `int16`，按“16 个低字节 + 16 个高字节”存放，一次查表 = 两条 `vpshufb`。
- **真正的二值对称性（生成侧）**：取反全部 4 个权重位会使每项符号翻转，即 `T[c ^ 0xf] = -T[c]`。
  因此只需对 `c = 0..7` 求和，另外 8 项直接取负填入，生成量为原来的 ~1/2。
- 权重一次性置换为内核需要的布局：每 32 行 × 每 4 个 K 位置共 16 字节，存放 32 个 4-bit 码
  （每字节 2 个码）。这是纯置换，存储量与 1-bit 权重相同（1 bit/权重）。
- 置换按张量惰性执行，并在 worker 线程间按行组并行填充（首次约 0.7 s），结果缓存在进程内。
- 置换同时把每 128 权重的 fp16 尺度 `d0` 收集为连续数组，使 GEMV 不再触碰原始张量（否则会
  以 576 B 步长零散读取原始张量，DRAM 流量翻倍）。
- 激活表按 128 权重一块累加 `int16`（上界 `32×4×127 = 16256`，不溢出），最后乘 `d0·d1`。

### L1 约束与 K 分块

整表大小为 `K/4 × 32 B = 8 B/权重`：K=4096 时 32 KiB（占满 32 KiB L1d），K=12288 时 96 KiB
（溢出到 L2）。按 BitNet TL 的做法实现了可选 K 分块 `GGML_Q1_LUT_KB`（块表 ≤ 16 KiB）。
K 分块对照（`-p 64 -n 128 -t 6`）：KB=1024 ~11.0、KB=2048 ~11.1、KB=4096 ~11.9、
整表(KB=0) ~12.0 —— **整表直写（默认）最优**，K 分块开关仅保留作实验。

### 整机实测（复核，2025-09-23）

早前一次测量曾得出“tg 持平、pp 查表更慢”的结论；复核（同场交替 A/B、控制预热与运行顺序）
后发现那是当时降频/后台负载造成的假象。正确结论是：

- **tg**：打包 GEMV 是计算瓶颈（约 9.8 t/s），查表内核把它推到单通道 DRAM 带宽上限（约 13 t/s）。
  本机 `-p 64 -n 128 -t 6` 受控 A/B（off/lut 交替）为 **9.70/9.99 → 13.04/13.01 t/s（约 +30%）**。
- **pp**：从 `ne11 >= 8` 起，查表全面快于 2×4 分块 GEMM，且 batch 越大优势越大：

| 测试 | 分块 GEMM (t/s) | Q1LUT pp (t/s) | 变化 |
|---|---:|---:|---:|
| pp8    | 16.9 ~ 18.3 | 20.8 ~ 23.7 | ~ +27% |
| pp64   | ~ 17.0 | ~ 21.4 | +26% |
| pp512  | ~ 15.8 | ~ 19.9 | +26% |
| pp1024 | 19.68 | 24.82 | +26% |
| pp2048 | 14.58 | 22.86 | +57% |

因此默认策略是**按实际要处理的 token 数选择**：`ne11 == 1`（tg）与 `ne11 >= 8`（pp）走查表；
`ne11 = 2..7` 走 2×4 分块 GEMM（此时查表建表尚未摊薄，且 `-n` 之外的通用路径也更省内存）。
可用 `GGML_Q1_LUT_PP=0` 强制 pp 走分块 GEMM。代价：首次为每个权重张量生成查表码（首次约 0.7 s），
额外约 0.95 GiB 内存。

### 单线程内核微基准

`bench/bench_lut2.cpp`（自包含、独立实现，含正确性校验，另有 K 分块变体）：

| 内核 | GMAC/s |
|---|---:|
| 现有符号 GEMV（Q8_128，单列） | 25.9 |
| **二值激活查表 GEMV（32 行，整表）** | **46.2 (+78%)** |

内核是快的；但整机 tg 是带宽瓶颈，内核速度被内存掩盖。

### 结论

- **tg 默认走查表**：打包 GEMV 是计算瓶颈，查表约 **+30%**（已到单通道带宽上限）。
- **pp 默认在 `ne11 >= 8` 时走查表**，全面快于 2×4 分块 GEMM（pp2048 +57%）；`2..7` 仍用分块 GEMM。
- 数值正确：PPL 同量级（LUT 5.7049 vs 不启用 5.7173，差异来自浮点求和顺序），长提示贪婪输出逐字一致。
- K 分块已实现且验证无收益；L1 表溢出不是该内核的瓶颈。
- 代价：额外约 0.95 GiB 内存、首次约 0.7 s 置换；`GGML_Q1_LUT=0` 可整体关闭。
- 线程数不应超过物理核；本仓库默认即为物理核（不启用超线程）。

## 为什么没有做 AVX-512 512-bit tile

评估过，但放弃，原因：

1. Q8_0/Q8_128 块布局是 34/130 字节，无法直接 64 字节对齐加载，需要 2 次 load + insert。
2. 每个 512-bit 半块需要构造 `[d1_0 ×8, d1_1 ×8]` 向量并额外 `mul`，开销抵消了宽度优势。
3. 本机无 AVX-512，无法验证运行时正确性；若引入未测试的崩溃风险，违背“正确运行”要求。

AVX-512 CPU 走 **VNNI 256-bit 路径**，已经获得指令级收益。
